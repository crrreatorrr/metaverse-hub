# PR11 atomic advancement draft (0054, depends08–10)

## Inputs and trust boundary

Only the PR10 scoped, current service principal may submit. The TypeScript result hook verifies exact bounded transport shape before calling a single SQL advancement function. The function independently locks/rechecks the durable principal's identity, scope, token/key binding, revocation and expiry at actual database time after locks; preflight is not completion authorization. Service auth credentials stay out of immutable worker/result/ack JSON. Staging an authenticated worker result in PR10 is not authoritative advancement.

PR10 deliberately does not stage full result checkpoints. Its authenticated wrapper calls `game.shooter_verification_commit_worker_result(account,worker,key,request_id,request_sha,body)` inside a principal-locked transaction, then rechecks actual expiry after all downstream waits and atomically stores its immutable digest/ack receipt. PR11 replaces that hook only. The exact body is `{manifest,result:{kind:'replayed',binding:claim,privateCheckpoint,publicResult}}`. Request SHA is SHA256('result\n'+stableSortedJSON(body)), independent of requestID/auth. The hook also computes a PostgreSQL canonical JSONB body digest for semantic duplicate recognition across request IDs, retaining only that digest and bounded ack in the existing immutable attempt-result row, never a16MiB CP copy per attempt. After current principal auth, identical committed duplicates return their original ack even when the attempt lease has ended; changed results cannot advance an occupied attempt.

## Lock order and transaction

Coordinate the exact principal/config ordering with0053. Scheduler/account/run/job locks use PR08 order. Append takes input admission/account/session/run but never scheduler: completion never asks for those input-admission locks after run, avoiding a cycle. Settlement remains a separate future PR12 transaction. No replay runs while SQL locks are held.

Within the transaction:
1. Reauthorize service principal with current time and scope, use the exact validated result body and return immutable prior attempt commit ack if its body digest matches.
2. Lock scheduler -> scheduler account -> run -> job. Recheck worker owner, fence, live lease and absolute deadline; compare run revision and verified cursor against the mutable job continuation predecessor. Require run/account/original-session identity and immutable job range, initial revision, original full-batch digest, exact bound manifest.
3. Validate the complete worker checkpoint and result against server-owned issuance and predecessor, including source checkpoint schema2, nested snapshot schema1, exact manifest/binding/issuance, bounded JSON, corruption checks and counters below. The worker is a trusted scoped simulator; do not replay expensive simulation in Nakama or mislabel a content hash as authentication. Structural/schema validation must not accept fabricated public worker JSON.
4. Operational zero-progress/no-checkpoint result routes to the same fenced retry transaction semantics (bounded attempt/backoff/quarantine), never invalid gameplay. Invalid-gameplay classification requires an authenticated valid bound worker verdict and current fence; stale failure cannot close a newer run.
5. A strictly monotonic complete checkpoint updates run checkpoint+strong SHA+cumulative counters/revision. Atomically write append-only attempt result and immutable commit receipt. A retryable partial result keeps the same job's original planned range/digest/initial revision, updates mutable expected_revision and continuation_tick, releases the attempt and sets durable retry/backoff. A resolved planned range completes the job with immutable verified ack. One logical active chain remains enforced; the next lazy predecessor-ready claim can materialize only after this commit.
6. On first terminal evidence, latch exact result/terminal tick, original accepted_sequence/tick highwater under the run lock, and payment pending/none without credit. Set run lifecycle terminal so new append cannot race after the latch. Any accepted tails captured by highwater remain eligible for structurally validated continuation. Preserve existing terminal object byte-for-byte on later suffix results. Retrying an earlier terminal cannot overwrite its result.
7. Return only allowlisted ack/cursors/revision/support state, never privateCP or full terminal details. PR10 service transport can use a separate bounded private projection when it next claims work. Owner status projects receipt-independent verified state and operational reason but no private snapshots.

## Exact accounting

The source checkpoint's accepted count is the prefix admitted to the incremental engine, not Hub's potentially farther-ahead accepted history. For a job in batch sequenceS:
- Source acceptedFrames must equal that original batch tick0+n after accept/step (or prior prefix only for begin initialization), batches=S+1; accepted bytes=(tick0+n)*16; actions is sum of immutable actions throughS. These may be <=Hub accepted counters and must not replace them.
- Source verifiedFrames must increase from run.verified_tick by at least1 for advancement and be <=job.tick_end; verifiedFramesTextBytes=verifiedFrames*16.
- Fully verified batches count is S when inside batchS, S+1 at its end; run.verified_sequence=verifiedBatches-1. Partial first batch keeps verified_sequence=-1. Exact action count is a prefix sum of immutable actions with batch.tick0+action[0] < verifiedFrames; all actions count once, including structurally resolved post-terminal suffixes.
- Snapshot counters.frames=verifiedFrames, segments=verifiedBatches. Snapshot state.tick=simFrames and simFrames<=verifiedFrames. Before terminal simFrames=verifiedFrames; after terminal simFrames and first-terminal snapshot/hash freeze even when verifiedFrames advances over input tails.
- Pending batch is null at the original batch end. Otherwise pending.batch equals the exact immutable original full batch and sha256; pending.cursor=verifiedFrames-originalbatch.tick0. A partial planned job may complete before the batch ends, leaving that pending batch in the authoritative checkpoint for the next job.
- Public worker projection must exactly match private accounting/terminal and be separately whitelisted. Matching public numbers alone never authorizes persistence.

The checkpoint full-JSON byte bound must include PostgreSQL's stored representation, not merely a JS UTF8 estimate. Exceeding a storage/export bound is an operational pending/support event that retains predecessor, not invalid_gameplay. PR08 reserved a16MiB checkpoint slot before first claim; PR11 actual byte accounting cannot exceed that slot globally/per-account. One current authoritative checkpoint slot is replaced transactionally; append-only attempt receipts retain hashes/revisions but do not duplicate arbitrary16MiB snapshots. Input retention/deletion remains PR17, so no accepted bytes are removed.

## Terminal tail and completion nuance

A terminal may occur before planned job tickEnd. The source continues structurally resolving the planned input range with frozen sim tick. Prefer completing that planned range before job completion, rather than manufacturing a new public suffix batch/digest. Early runtime timeout may persist terminal+partial verified cursor on the same job. Future job claims can verify accepted tails up to the latched Hub highwater, deriving acceptedBeforeTerminal from server sequence/highwater, never a public boolean. New distinct input after latch is refused by append. A seal/expiry without terminal eventually resolves as incomplete without payment; finish/expiry lifecycle interfaces must be completed before client rollout.

## Implemented PR11 boundary and evidence status

This branch replaces the PR10 result hook additively in migration0054. No wallet, ledger, receipt, economy-cap or ranking operation is added. First terminal stores a stable terminal_revision and server accepted highwater; only a clean eligible clear becomes payment pending, and other terminal outcomes become ineligible. Later input-tail resolution preserves the first terminal and any later settlement state. Actual settlement remains PR12.

The bounded TypeScript validator performs no simulator steps: it validates exact private envelopes, FNV corruption checks, finite state/IDs/counters, canonical parts classification and quantized terminal state hash. It distinguishes the snapshot's16KiB string/key bound from the outer pending batch's2MiB string bound. SQL independently checks server-owned identity/manifest/issuance/full-batch digest/range/pending cursor/cumulative accounting before committing. FNV/state hashes do not authenticate workers. The configured scoped verifier and exact approved external simulator remain trusted components; this does not defend against a compromised authorized simulator that fabricates valid state.

Checkpoint malformedness and server-state/issuance failures stay operational pending, never gameplay cheating. A narrowly allowlisted deterministic cheat result can close only its live fenced predecessor, and cannot invalidate an already latched terminal. The result-retry overload writes immutable semantic digest/ack before releasing its attempt, so identical operational and zero-progress result duplicates recover the same acknowledgment across request IDs as well as through the PR10 receipt. Immutable attempt ownership is checked even for successful duplicate recovery.

The test matrix includes the actual entire9634-frame frozen Sahil clear through three planned jobs, a real failure with accepted suffix, first partial batch continuation, same/different request IDs and workers, conflicting branches, rehashed invalid state/terminal/oversized snapshot strings, frozen post-terminal state, original session expiry and a lock wait across lease expiry. Execution and review are pending exact-head GitHub Actions; no local implementation tests or builds were run. General full-stack integration remains a separate required check.
