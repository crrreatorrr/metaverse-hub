# Durable verification schema (PR 06)

Migration `0050_shooter_verification_queue` follows the inspected root-registered `0049_sproto_duel_wager_flag`. It is automatically discovered through the `src/games/*.ts` compiler glob and `HubSchema.register`; no RPC, worker or issuance gate is registered. Before merging, recheck current main and overlapping PRs for a newly allocated migration number. Applied migration bodies/checksums remain unchanged.

The additive tables are separate from the authoritative legacy run, receipt and wallet tables:

- `shooter_verification_run` binds the exact original owner/session to a legacy run and stores upload/simulator/checkpoint/economy versions, exact artifact SHA/source commit, revision, separate accepted/verified input cursors and simulation tick, cumulative byte/action/batch counters, terminal/checkpoint state, payment status and timestamps.
- `shooter_verification_batch` stores immutable `(run_id, sequence)` inputs, range, request digest, original received acknowledgment, acceptance time and the lease-validity evidence observed at acceptance. Updates/deletes are rejected. A later reviewed retention migration must define safe payload replacement/removal; this foundation cannot delete accepted evidence.
- `shooter_verification_job` records the input range, expected revision/digest, queue state, lease owner/deadline, fencing token, bounded retry budget, durable retry time and verified acknowledgment. A partial unique index permits only one ready/leased/retry-wait chain per run; blocked future work is separate.

An exact composite foreign key binds metadata to `shooter_run(run_id,user_id,session_id)`. Partial indexes support active-account admission, expiration/recovery, bounded owner status, claim/reclaim and run history. Database checks enforce 2 MiB batch/64 MiB run encoded-byte ceilings, 162000 ticks, action/batch ceilings, cursor ordering, lease shape and retry bounds. These are schema backstops: the ingestion/claim/result transactions in PRs 07–11 must additionally enforce authenticated authorization, canonical decoding, contiguity, row/counter consistency, predecessor checks, monotonic revisions and fencing. DDL alone does not implement those operations.

Private JSON checkpoint storage has a 16 MiB safety ceiling; terminal/acknowledgment JSON is bounded at 64 KiB. These storage ceilings are not measured simulator checkpoint sizes or approval to enable an artifact. PR 03 must measure a complete checkpoint's size/depth and enforce a supported bound no greater than storage capacity before issuance can use it. Versions/artifact values are mandatory with no fictional default artifact. Job attempt limits must be supplied explicitly. No wallet credentials, grace periods, payment amounts, client inventory or production secrets are seeded.

`verified_sequence` is the last **fully resolved** public batch; a first partial verifier slice can advance `verified_tick` and `simulation_tick` while `verified_sequence=-1` and `verified_batches=0`. Job range identity includes tick bounds so successive slices inside one upload batch can retain separate durable attempts/results. Terminal simulation tick must equal the latched terminal tick even if the verified input cursor later advances over accepted trailing input.

Owner D01 remains unchanged: original-session authorization must be live at actual locked settlement time, with no post-expiry payment grace. `authorized_lease_until` is acceptance evidence only and cannot authorize a later settlement. Expiry can release the active-admission slot while accepted work remains retained. Terminal verified state and payment status remain separate; existing receipts/ledger stay authoritative.

Unit registration checks run under `npm test`. Real SQL checks are wired into `npm run test:dup` as `DUP_ONLY=shooter-verification`, including fresh boot/checksum discovery, real constraint/immutability violations, a populated legacy upgrade and unchanged ledger/balance snapshots, and repeated boot without migration reapplication. The focused Actions workflow creates throwaway test credentials and Compose services only. Full existing migration tests also discover the new migration from source and exercise checksum/order/cold-boot behavior. No local implementation tests, production migrations or deployments are authorized by this PR.
